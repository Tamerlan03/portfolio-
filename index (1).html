КЕЙС 01 — МОБИЛЬНОЕ ПРИЛОЖЕНИЕ
Self-service tariff change in mobile app
Пользователь меняет тариф в приложении без обращения в поддержку.
ТребованияUser FlowAPIQA
+
Проблема

Смена тарифа возможна только через звонок в call-центр, что создает нагрузку на поддержку и увеличивает время операции для абонента.

Бизнес-цель

Снизить нагрузку на call center и увеличить долю самостоятельных операций в мобильном приложении за счет запуска сценария смены тарифа.

User stories
Как абонент мобильной связи, я хочу видеть доступные тарифы и менять текущий тариф в приложении, чтобы управлять услугами без обращения в поддержку.
Acceptance criteria
  • Пользователь видит только тарифы, доступные для его типа номера.
  • Если на балансе недостаточно средств, система показывает понятное сообщение.
  • При успешной смене тарифа пользователь получает push/SMS-уведомление.
  • Если биллинг недоступен, операция не проводится, пользователь видит техническое сообщение.
  • Все действия логируются для последующей аналитики.
Сценарий пользователя
Главная → Мой тариф → Сменить тариф → Список тарифов → Детали тарифа → Подтверждение → Результат
Схема интеграций
Mobile App → API Gateway → Product Catalog Mobile App → API Gateway → Billing System Billing System → Notification Service Billing System → Event Tracking / DWH
API endpoints
GET /api/v1/users/{userId}/available-tariffs POST /api/v1/users/{userId}/tariff-change GET /api/v1/tariff-change/{requestId}/status
QA / тест-сценарии
  • Успешная смена тарифа
  • Недостаточно средств на балансе
  • Тариф недоступен для типа номера
  • Повторная заявка на смену тарифа
  • Ошибка на стороне биллинга
  • Пользователь без авторизации
  • Задержка ответа от внешней системы
Ожидаемый эффект: снижение количества обращений в поддержку, ускорение операции смены тарифа, рост доли self-service в приложении.
КЕЙС 02 — ЛОЯЛЬНОСТЬ / ПРОДУКТОВАЯ АНАЛИТИКА
Loyalty bonus program for mobile subscribers
Бонусы за пополнение баланса, оплату услуг и активность в приложении.
МетрикиСобытияAcceptance Criteria
+
Проблема

Низкая частота повторных операций в приложении — пользователи не возвращаются после разовых действий (оплата, пополнение).

Продуктовая цель

Увеличить retention и частоту использования мобильного приложения через бонусную механику.

User stories
Как пользователь, я хочу видеть количество бонусов, чтобы понимать свою выгоду.
Как пользователь, я хочу списывать бонусы на услуги связи, чтобы экономить на оплате.
Как продуктовая команда, мы хотим видеть аналитику использования бонусов, чтобы оценивать эффективность программы.
Acceptance criteria
  • Баланс бонусов отображается в личном кабинете.
  • Пользователь видит историю начислений и списаний.
  • Бонусы нельзя списать на недоступные услуги.
  • При ошибке списания бонусы не должны исчезнуть.
  • Все операции попадают в аналитику.
Ключевые метрики
  • MAU / DAU
  • Conversion to bonus activation
  • Repeat payments
  • Retention 30 / 60 / 90
  • ARPU, churn rate
События (data events)
EventКогда срабатываетОсновные поля
bonus_activatedпользователь подключил бонусную программуuser_id, segment, source, timestamp
bonus_redeemedпользователь списал бонусыuser_id, amount, service_type
bonus_error_shownошибка при операцииuser_id, error_code, step
Ожидаемый эффект: рост повторных операций и retention, более точная оценка эффективности бонусной механики на уровне продукта.
КЕЙС 03 — CRM / ПОДДЕРЖКА
Customer support request flow automation
Заявка в приложении → CRM → SLA-обработка → статус для клиента.
BPMNИнтеграция с CRMSLA
+
AS-IS (как сейчас)

Пользователь пишет в чат или звонит, оператор вручную создает обращение, статусы не всегда прозрачны для клиента.

TO-BE (как будет)

Пользователь создает заявку в приложении, система автоматически определяет категорию и передает её в CRM, клиент видит статус в реальном времени.

Процесс
User submits request → System validates request → CRM creates ticket → Support team processes ticket → Status update sent to user → Ticket closed
Интеграция
Mobile App → Backend → CRM CRM → Notification Service CRM → DWH / Reporting
Статусы SLA
  • Created
  • In progress
  • Waiting for customer
  • Resolved
  • Closed
  • Rejected
Acceptance criteria
  • Заявка создается только после валидации обязательных полей.
  • Клиент получает номер заявки.
  • Статус заявки обновляется в приложении.
  • Просроченные заявки попадают в отчет по SLA.
  • Заявки доступны для аналитики по категориям и времени обработки.
Ожидаемый эффект: сокращение ручных обращений в поддержку, ускорение self-service операций, прозрачность клиентского пути.
Важное уточнение. Большинство коммерческих проектов выполнялись под NDA, поэтому данное портфолио содержит обезличенные демо-кейсы, основанные на реальной логике аналитической работы: анализ требований, продуктовая логика, интеграции, потоки данных и QA-сценарии. Конфиденциальные данные, названия клиентов и внутренние системы не раскрываются.
